# Resolved decisions

Resolutions of the open questions in `design.md` §10, plus environment facts.

## Environment
- Blender 5.2 LTS, bundled Python 3.13 in blender.org's builds (a distribution-packaged Blender may use the system `/usr/bin/python3.14`). Grease Pencil is the v3 API (`bpy.types.GreasePencil` with layers, drawings and attributes) — the 4.2-era GP API does not apply.
- **Python 3.13 and 3.14 both** (2026-11-04): official blender.org 5.2.3 bundles 3.13.13 and a distribution's build may use 3.14, so `venv.compatible()` accepts either (`venv.PYTHONS`). One lock serves both: it was compiled for 3.14, but its hashes cover each pin's 3.13 wheels too, so it stays as it is.
- Extension format: `blender_manifest.toml`, minimum Blender 5.2: the Grease Pencil v3 API, and the lock's wheels are built for its Python, so an older Blender would install the extension and then fail.

- **Platforms** (2026-10-23; `linux-arm64` added 2026-10-23): `linux-x64`, `linux-arm64`,
  `windows-x64` and `macos-arm64`, in one extension zip. Linux x64 is the only one used for real;
  the README's Platforms table says how far the others have got.
  - One lock for every platform. It was compiled for manylinux x86_64, but uv's
    `--generate-hashes` wrote the hash of every file of each pin, so the Windows x64
    and macOS arm64 wheels of all 30 compiled pins at their pinned versions already verify
    under `--require-hashes --only-binary :all: --no-deps`. The one package a Windows
    resolve adds is `pywin32` (`mcp` requires it on win32), which the lock pins by hand.
  - **`pywin32` 311 in the lock, for Windows only** (2026-11-05). It was first left out
    on the belief that `mcp` guards the import and only its stdio client uses it. Neither
    is so: `mcp` 2.3.0's `mcp/os/win32/utilities.py` imports `pywintypes`, `win32api`,
    `win32con` and `win32job` unconditionally on win32, and `mcp.server` reaches it through
    `mcp.server.stdio`, so importing the SDK fails without them. Whittle's in-process
    servers do not help, and the first Windows CI run stopped there
    (`No module named 'pywintypes'`). 311 is the floor `mcp` declares (`pywin32>=311`),
    the oldest release with wheels for both Python 3.13 and 3.14 (310 has no cp314), and
    public since July 2025 where 312 dates from June 2026. Its marker keeps it off Linux
    and macOS, and only its two `win_amd64` hashes are listed, the rest being wheels no
    supported platform installs. The entry is added by hand because the lock's recorded
    command targets Linux and would drop it; `tests/agent/test_venv.py` fails if a
    recompile does.
  - No Intel Macs: `cryptography` 50.0.2 has no macOS x86_64 wheel (upstream dropped them
    in 49), and Blender 5.2 has no Intel Mac build. No Windows on Arm: the SDK has no
    `win_arm64` wheel.
  - Linux arm64: PyPI's JSON API, asked for each of the 30 pins at its exact version,
    lists the CPython 3.13 and 3.14 manylinux/musllinux aarch64, abi3 and pure-Python wheels, and
    every one's sha256 is already in the lock (the SDK's `manylinux_2_17_aarch64` wheel
    with its `claude` among them), so the lock installs there unchanged. Listed, untested.
  - One zip, not `extension build --split-platforms`. Splitting only filters the
    manifest's `wheels` entries per platform, to shrink uploads that bundle binaries;
    Whittle bundles none (pip downloads the platform's own wheels at setup), so it would
    make three identical zips.
  - Windows process handling: the agent and the setup steps start with
    `CREATE_NO_WINDOW`; the agent goes into a Job Object with
    `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (ctypes), since TerminateProcess does not reach
    the CLI the agent starts and there is no process group to signal. A Windows
    terminate is a hard kill, so the shutdown message is the graceful path there. Where
    the platforms differ, the code lives in `whittle/platforms.py` and takes the
    platform as an argument, so the Linux suite covers each branch.

## Agent process
- **Python**: Blender's bundled Python. The extension creates a private venv from Blender's `sys.executable` and installs `agent_env/requirements.lock` with `--require-hashes --only-binary :all: --no-deps`, after user confirmation in preferences. Never auto-upgrades.
- **SDK**: `claude-agent-sdk==0.2.167`, exact pins + hashes in `agent_env/requirements.lock`. The wheel bundles the Claude CLI (`claude_agent_sdk/_bundled/claude`, `claude.exe` on Windows), so no separate CLI install is required.
- **System-wide pip config** (2026-11-04): left as it is. Setup's `--isolated` skips the user's pip config but not a system-wide one, whose `extra-index-url`, `find-links` and `no-index` still reach it. `PIP_CONFIG_FILE=os.devnull` would close that, and also drop a proxy or CA set only in pip.conf. Why leave it: those keep working, and the hashes are the protection, since they decide what gets installed whatever the index.
- **Dev venv**: `.venv/` at the repo root, made from Blender 5.2's Python with the lock installed the way the add-on installs it (README, Development). Use `.venv/bin/python` for agent-side code and tests. Do not install anything else.
- **Auth** (changed 2026-10-23): an Anthropic API key only: the preference, else `ANTHROPIC_API_KEY` in Blender's environment. No key, no agent; the sidebar asks for one. The agent's environment loses every other Claude or Anthropic credential variable and the bundled CLI runs with Whittle's own `CLAUDE_CONFIG_DIR`, so it can never sign in with the user's claude.ai login, nor read their Claude settings, hooks or MCP servers (architecture §2, Authentication). Why: Anthropic does not allow third-party products built on the Agent SDK to offer claude.ai login or use subscription plan limits; developers are to use API key authentication. The earlier default, the user's existing Claude login, is gone.
- **Telemetry** (changed 2026-10-23): the agent runs with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, so the bundled CLI sends no usage telemetry or error reports of its own. The preference **Send Claude CLI usage data** (off) leaves the variable unset, and Blender's own environment, if it sets it, still wins. Why: Whittle's privacy promise is that only the turns go to Anthropic; telemetry is opt-in.
- **Model**: per chat, picked from the button beside Send (the newest of each family, older versions in a submenu, any id by hand); new chats start on the preference, default `claude-opus-5-5`. The list comes from the Models API through the key (older versions included), else the bundled CLI's initialize response, cached in the user folder over a bundled list (architecture §15). A change applies from the next turn via `set_model` in the same SDK session.
- **Effort** (2026-10-23): per chat, Low, Medium or High from the model menu; new chats run at High, with no preference. Opus 5.5 defaults to medium, and multi-step modelling turns gain from more thinking, so Whittle always sets it (`--effort`) rather than leaving it to the model. A change applies from the next turn in the same session via the CLI's `apply_flag_settings` control request, since the Python SDK has no effort method; restarting the session would also work but costs a reconnect.
- **Progress notes** (2026-10-23): Claude's short notes between tool calls are shown as its text. On Opus 5.5 they arrive as narration thinking blocks, which the bundled CLI requests (thinking display `updates`) as long as no explicit display is set, so Whittle sets none and turns narration blocks into text (architecture §5). Summarized thinking was the alternative; it is longer, reads as reasoning rather than as a message to the user, and would stop the updates.
- **The system prompt goes to the CLI by file** (2026-11-05): `runner.write_prompt` writes `.system_prompt.md` to the session folder and the SDK passes `--system-prompt-file`. Why: a full-size style guide no longer fits on a command line. A 148 KB prompt failed with "Argument list too long" with the real SDK and bundled CLI (Linux allows 128 KiB in one argument), and Windows allows 32 KiB for the whole command. The leading dot keeps it out of what a chat packs into the `.blend`.

## Behaviour
- **Branching**: fork the SDK session per branch. Each history node records the SDK session id at its completion; submitting from a non-leaf node resumes that session with `fork_session=True`.
- **Target lock**: removed (2026-10-23). It first warned the user and told the agent whenever the user touched the target during a turn, but it fired far too often (changing the viewport's shading counted) and the warning was noise. Now Whittle neither watches nor reports user edits during a turn: editing the target while Claude works is the user's call. Never block or revert the user.
- **Self-check renders**: Workbench at 512 px; `gpu.types.GPUOffScreen` viewport-draw path as the fallback if renders are too slow.
- **Self-check cap**: 3 rounds by default, configurable.
- **Per-file settings** (2026-10-23): every session setting (triangle budget, self-check rounds, render size, style notes) has a preference default and an optional override saved in the `.blend`, edited in the agent popover (`ui.md` §3.1).
- **One style guide, in a file** (2026-11-05): a single setting, Style Notes, holds the path to a `.md` or `.txt` file, and replaces the Palette, Bevel Style and Style Notes text fields. Empty means no guide, and the agent chooses. Why: the three overlapped, so nobody could tell what went where, and the docs did not settle it. A text box also lives in one `.blend`, and real work spans many: a large game has a general art style, different guidelines per faction and further splits per culture, across hundreds of `.blend` files and some twenty style notes that all reference many of the same files. A file on disk is written once and shared, and `//` paths let a project folder move. It stays a session setting, so a preference can set the default and a file its own. The guide reaches the agent as the user's preferences for the file, applied with judgement, not as rules; since it is a plain file that may be shared, the system prompt also says it speaks to the look only. The new key, `style_file`, means old inline text is never read as a path. Old values are not migrated: old preferences and scene keys are ignored, and files and bundles holding `palette`, `bevel_style` or `style_notes` still load.
- **Guide paths survive a repository's moves** (2026-11-05): a backslash in a relative path, `//` or an `@` import, reads as a separator on every platform, and a save into another folder rewrites each scene's `//` Style Notes to name the same file. Why: the `.blend` files and guides of a project live in one repository, cloned at different paths on Windows and Linux, and Blender only remaps its own path fields. A rooted path (drive, UNC, `\folder`) is left alone: `\\server` made `//server` would read as relative to the `.blend`. The cost is that a relative path cannot name a file with a backslash in its name, and a rewrite that would write one, from a folder so named on Linux or macOS, gives the absolute path instead. The rewrite is string maths from the old and new folders and never reads the guide, since the path comes from the file and saving is no reason to go where it leads; only the two `.blend` folders have their symlinks resolved, because a read's `..` walks up from a folder's real place, where Blender's own remap stays textual. An undo or redo across the Save As rewrites the path again, unlike an image path: a step from before it holds the old text, and counted from the new folder that can name another project's guide with no warning, and what it names goes to the API. Stamps beside the text say which folder it counts from, and they are for the session only, as a stamp read from a file could not tell an undo from a repository cloned elsewhere. A copy gets the new text and the open file keeps its own, the way `relative_remap` treats images. The preferences' `//` path stays: it is relative to whichever `.blend` is open. The agent's restart check ignores the path and compares the guide's text, which is all the agent gets, so a Save As restarts nothing. A move outside Blender cannot be followed: no save happens, and a `.blend` opened from a new place looks the same as a repository cloned elsewhere.
- **Imports are whole lines** (2026-11-05): a guide imports another with a line holding only `@path`, after trimming whitespace, and never inside a fenced code block. A path with a space in it has to end in `.md` or `.txt`. Why: guides are prose, and prose has email addresses and handles in it; an `@` anywhere in a line would turn those into imports, each one a false warning or worse, a file sent that nobody asked for. A whole line also says exactly where the text goes: it replaces the line, so the author controls the order. Paths are relative to the file importing, so a folder of guides works from any `.blend`. A file reached twice counts the first time only, so a shared base is not repeated, which also ends import loops with no case of their own.
- **A lone `@word` line warns** (2026-11-06): a line holding nothing but `@word`, such as a handle alone on a line, is read as an import like any other, and warns that it was refused, since `word` is not a `.md` or `.txt` file. Why: the line has exactly the shape of an import, so telling the two apart would be a guess, and staying quiet would hide a mistyped import, which leaves part of the guide unsent. A warning costs a look and sends nothing.
- **Only `.md` and `.txt` load, 128 KiB in all** (2026-11-05): judged on the path with its symlinks resolved, regular files only, and the files loaded are listed in the agent popover. Why: a `.blend` stores the path, and what loads goes to the API, so a file from someone else could point at a private file on the user's machine, directly or through an `@` line, and send its contents with the next turn. Private keys and credentials do not end in `.md`, and a `notes.md` link to one is refused because the check runs after the link is followed. This narrows the risk, and does not end it: a private `.md` file can still load, which is why the list shows everything being sent. The cap bounds what a guide can add to every turn; past it, loading stops with a warning.
- **A guide never fails a turn** (2026-11-05): a missing or unreadable file or a refused import, the top-level file included, is a warning in the sidebar and one line telling the agent that part of the guide is missing; the turn runs with what loaded. Why: a guide is guidance, and a moved file should not stop the work. The agent gets a yes or no, not the problems, so local paths do not reach the API that way.
- **Opening a file reads nothing it names** (2026-11-05): `load_post` reads only the preferences' own guide, and the field offers **Read Now** for the file's. Why: the path is the file's and nothing the user did asked for it. On Windows, opening `\\host\share\x.md` can hand a stranger the user's NTLM credentials, and on any platform a dead share blocks the UI until it times out; Blender's Auto Run does not gate this. Sends and saves still read, including from shares, since studios keep guides there. Rejected: reading on a worker thread, which ends the blocking but not the connection; refusing UNC paths at load, which misses `/net/host/x.md` under autofs. The cost is that the list is empty until asked for, which is what the button is for.
- **A guide is read again before each turn** (2026-11-05): a combined text that changed restarts the agent before that turn, as a changed setting does, and amends within a running turn do not reread. Why: an edit to a shared guide has to reach every `.blend` using it, and the system prompt is fixed for a session, so a restart is the way in.
- **Distribution** (changed 2026-10-23): open source under GPL-3.0-or-later (the license Blender add-ons that import `bpy` take). Built from the repo with `build.sh`; not on extensions.blender.org yet. Branding follows Anthropic's Agent SDK guidelines: Whittle is its own product, "Powered by Claude" at most, never named or styled as Claude Code, and not affiliated with Anthropic.

## Shortcut
- **Key**: Shift+Alt+C (`whittle.type_prompt`, an add-on item in the Window keymap, so it works over any editor and in every mode, and is rebindable in Preferences → Keymap). C for Claude or chat, and one hand reaches all three keys. It is unused in Blender 5.2's default keymap outside modal maps, which only apply while their own operator has the keyboard (C toggles clamping while moving or bevelling); `tests/blender/test_shortcut.py` checks this against the default keymap's source. Background Blender has no key configurations (`wm.keyconfigs.default` is empty), so the keymap was dumped from `presets/keyconfig/keymap_data/blender_default.py`, the source Blender builds it from. Rejected: Alt+Space, which desktops often take (launchers, the window menu); Shift+Space (the tool menu); Ctrl+Shift+Alt combinations, hard to hit with one hand; F-keys, far from the home row.
- **Popup, not the sidebar's box**: Python cannot start editing a sidebar field. So the shortcut opens the sidebar on the Whittle tab (`Region.active_panel_category` is writable in 5.2.2, but only once the region has drawn and listed its tabs, so a hidden sidebar is retried on a timer) and `wm.call_panel(keep_open=False)` of a panel under the pointer whose field has `UILayout.activate_init`, as Blender's own F2 rename does.
- **One line**: the multi-line `textbox` ignores `activate_init` (checked in a GUI Blender: nothing typed reached it), so the popup holds a one-line `prop` of the same string. Shift+Enter cannot add a line there; long prompts belong in the sidebar.
- **Panel popup, not a props dialog**: in `invoke_props_dialog` the first Enter only ends text editing and a second presses the dialog's button. In a panel popup Enter confirms the field and closes the popup on the press, so the release reaches `whittle.enter_send` and one Enter sends, exactly like the sidebar's box. Checked in a GUI Blender with `--enable-event-simulate`: Shift+Alt+C, typing and Enter sends a prompt, an amendment and an answer with the fake agent, in Object Mode, Edit Mode and sketching; Esc sends nothing and keeps a draft.

## Sketching
- **One plain stroke** (2026-11-05): a stroke is just a stroke. It goes on one Grease Pencil layer, with nothing to pick before drawing. Why: Whittle started as a replacement for the 3D object functionality of Claude Design, where the only sketch markup was redlines. Those were simple but highly effective, because the text of the prompt steered Claude in the right direction: the mark says where, the words say what. The stroke types of `design.md` §3 (free, add, carve, crease, region and note, each with a layer, colour, meaning, icon and sidebar button, and Shift+Alt+N to step through them) were built and then removed: they were not useful in practice and they cluttered the UI. The system prompt's "Reading the sketch" tells the agent that strokes are markup whose meaning comes from the prompt, with a stroke's shape and what it lies on as its guide when the prompt says little.
- **Strokes are red** (2026-11-06): `sketch.STROKE_COLOUR` is a redline red, not the white the plain stroke started as. Why: the sketch is a redline, so it should look like one, and white gets lost on a pale model. Red reads on a wooden crate and on the agent's grey backdrop alike, in the viewport and in the overlays. The colour still means nothing, as the system prompt tells the agent.
- **No format bump**: `request.json` lost `stroke_types` and each `strokes.json` entry lost `type`, but `formats.VERSION` stays 1, because `_check_header` rejects any other version and older chats would stop opening. The validators ignore the old keys and `from_json` reads only known fields, so older session folders and chats still read; their strokes come back on the one layer, red. The check is strict, so a bump would refuse every request v0.1.0 stored.
- **Older `.blend` files need no migration**: the old per-type layers stay in the file, and every layer of the sketch object is read, so those strokes are still counted, sent, stamped, removed by a finished turn and wiped by Clear. They keep their old colours and fills until then, the white of the old `free` layer included: only `Strokes`, the layer new strokes go on, is tinted red, and that tint is set each time the layer is used. A layer someone added to the sketch object by hand is read too.
- **Skill names stay**: `boolean-carve` and `bevel-crease` name the modeling technique. Their descriptions now say when a stroke marks material to remove or a hard edge.

## Sketch keys and view markers
- **Keys**: Shift+Alt+D toggles Sketch mode (`whittle.sketch_toggle`), Shift+Alt+V captures a view, and Shift+Alt+Enter sends (`whittle.send_key`: Send between turns, Amend while Claude works, as Enter in the prompt box does). Add-on items in the 3D View keymap, which applies over the viewport in every mode, Draw Mode included, so one binding serves starting, drawing and sending; listed and rebindable in Preferences → Keymap (3D View → 3D View (Global)). The same Shift+Alt pair as Ask Claude, so a tablet's express keys map to one family of chords, with letters that name the action (D draw, V view, Enter sends as in the prompt box). All three are unused in Blender 5.2's default keymap outside modal maps; `tests/blender/test_keys.py` checks them against `blender_default.py`. Checked in a GUI Blender with simulated keys over the viewport in Draw Mode: V captures a view, D leaves and re-enters Sketch mode; the `send_key` GUI check presses Shift+Alt+Enter between turns and during one. Rejected: keys in the Grease Pencil Draw Mode keymap only (the toggle must also work from Object Mode, and two homes in Preferences are harder to find); bare letters (all taken in Draw Mode).
- **Keys send on their own operator**: Shift+Alt+Enter and Enter in the box run the send body with their own operator (`operators.key_send`), not `bpy.ops.whittle.submit`. Why: Blender raises a nested operator's error report in the caller as `RuntimeError`, so the user would get a Python traceback in place of the error line.
- **Markers as gizmos**: a gizmo group gives hovering, highlighting, picking and the click for free, hides with the viewport's Gizmos overlay, and keeps a constant size on screen; a draw handler would need its own hit-testing and a modal operator watching every click. A click on a marker reaches the gizmo before the Draw tool (checked in a GUI Blender: no stroke is drawn). Markers show only while sketching, when they help pick a view to return to, and `whittle_show_view_markers` (the view list's **Markers While Sketching**) turns them off.
- **Snap pose**: the snap restores the view's eye, direction and field of view exactly, but not the pivot, which views do not store: a perspective snap orbits around the view's own strokes (their mean depth), so orbiting afterwards turns around what was drawn. A snapped-to view becomes the current one, so strokes drawn from it join it instead of making a near-duplicate view.

## Chats
- **Model**: a file holds many chats; each has its own conversation, history tree and SDK sessions (its folder is the agent's cwd). Switching chats leaves the scene as it is and only changes the conversation and the agent's context; the next turn starts from the scene as it is, with a context note. New Chat and switching wait for a running turn.
- **Storage**: everything is stored inside the `.blend`, so the file alone carries every chat. Each chat is one zip (`.png`/`.blend` stored, JSON deflated; turn checkpoints and comparisons left out) in a `bytes` ID property on a hidden `.whittle` Text, written in `save_pre` and removed in `save_post`; `load_post` unpacks into the file's cache and removes it. Why: `bytes` ID properties are exact, fast (5 MB in 2 ms) and leave the file when deleted (5.54 → 0.54 MB on the next save). Kept in Blender's data between saves they would make every undo step slower (6 vs 1 ms per push at 50 MB), hold the payload twice in memory, and let Ctrl+Z roll chat data back with the scene; written only around a save they cost undo nothing. Rejected: Text datablocks with base64 (a 6.8 MB line hung Blender; 3× the size in lines), packed files (only images, sounds, fonts and volumes), snapshots as real datablocks (in every undo step, the outliner and the user's file data).
- **Cache** (changed 2026-10-23): nothing is written beside a `.blend`. The working copy is a hidden cache, `<user dir>/cache/<file id>/`, named by a random id stored in the `.blend` (a string ID property on the same Text, kept in the data), so it survives renames and moves; an unsaved file gets its id with its first chat and keeps the cache when saved, so nothing moves on a save. A copy opened while the original's cache is claimed by a live Blender, or whose cache records a different file that still exists, gets a fresh id (copy-on-conflict), so two files never share one cache; until the copy is saved with that id, each open finds the same cache again by its recorded path, so a crash before the first save loses nothing and no stray caches pile up. The `.blend` stays the truth: opening it fills the cache from it and a differing cache copy is deleted, except for crash recovery: when the cache's recorded `base` (a stamp of the index and zips the `.blend` last stored or opened with) equals the opened file's, the cache's newer work stays, since Blender's autosave and crash files carry no chats. Caches not used for 30 days are deleted whenever a file is opened (and when the add-on is enabled with one open), never the open one. Why: folders beside a `.blend` are clutter; the earlier `<name>.whittle/` sidecar (and `.replaced-<time>/` folders on conflicts) cluttered every folder with a saved `.blend`. Repacking only chats whose folder changed (a stat fingerprint) keeps saves fast.
- **SDK transcripts**: carried with the chat through the SDK's `SessionStore` (a folder store in the chat's `sdk/`), so a chat resumes on another machine or after the file moved. They count towards the chat's size (about 0.1–0.3 MB per turn with render images).
- **Deletion**: a chat is deleted from its trash icon or in bulk (all others, or older than a week, a month, three months), always after a confirmation; it leaves the cache and the CLI's project folder for its cwd at once and the `.blend` at the next save. The menu shows each chat's stored size so growth is visible. Deleting the current chat switches to the most recent remaining one, or a new empty chat.
- **No migration** (changed 2026-10-23): the code that moved earlier layouts into the cache (a single-session folder, the `<name>.whittle/` folder beside a file and its `.replaced-<time>/` copies, the user folder's `caches/<sha1>/` and `dev-sessions/`) is gone. Why: those layouts come from development builds before 0.1.0, which no released file uses, and the code had to be carried and tested through every change to the cache.
- **Same file in two Blenders**: the second still gets a cache of its own (copy-on-conflict), so neither overwrites the other's chats; while the other Blender has the file, which its open mark says (or its claim, on a recovered copy), the sidebar has one quiet line: "This file is open in another Blender; chats here won't merge with it." It shows on files with no chats too, because each Blender marks the saved file it has open. Why: merging two caches of one file is not worth its complexity, but silently diverging chats surprised.
- **The transcript is a view**: Open Transcript shows the stored chat in a runtime Text, never data of the file: no save keeps it, whatever Save Chats says, and it ends with its chat, also when an undo step from before the delete brings it back. Why: a transcript left in a `.blend` would carry a chat out of a file the user had deleted it from, or kept chats out of.
- **Images too big for a request**: the add-on refuses a request over `formats.REQUEST_IMAGE_BYTES` when it writes the bundle, and a turn that fails for size offers Edit, not Retry. Why refuse at the bundle: past that size the CLI exits on one line of stdin and the session goes with it; recognising that from the CLI's stderr would depend on its wording and race its exit. Why not downscale: the image is the user's, and what to drop or shrink is their call. Why no Retry: the same images would fail the same way. Why the reason is so short (2026-11-04): the sidebar gives a turn's reason two lines, so `Images too big: send fewer or smaller` shows whole at the default width, and the fuller advice (a new chat, when the conversation already holds many images) lives in the docs site.
- **Chats from another machine**: each chat records the install that made it (`origin`, a random id in Whittle's user folder, `install.json`, naming no person or machine). A chat whose origin is another install opens with a box, "Continue this chat?" [Continue]; Send is disabled with a tooltip until then, and New Chat stays available. Continue records this install in the chat's `adopted` list, stored with the chat, so it never asks again here, and the file saved from here carries that. Chats from before the marker count as this install's: no prompt for existing files. A user's own chats ask once on each of their other computers too; that is intended. Why: continuing a chat replays its conversation to Claude as if it were Claude's own, so text planted in someone else's file could steer it (README, Security); one click is cheap, and the default is the safe one. Going back in such a chat's history stays allowed before Continue (2026-11-04), though it changes the scene: the gate exists to stop text going to Claude from a chat this install did not start, and looking through it helps the user decide.

## Continuous integration

- **GitHub Actions on free standard runners** (2026-11-04), with a GitHub Release as the
  output. No larger or self-hosted runners and no secrets; publishing uses `GITHUB_TOKEN`
  in the one job with `contents: write`, which checks nothing out.
- **Blender from download.blender.org, not a package**, so CI runs what most users run.
  The version and each archive's SHA-256 are pinned in `.github/scripts/fetch_blender.py`,
  from Blender's published `.sha256` file, and checked on every use, cached or not, so the
  cache is not trusted.
- **Blender's mirrors as a fallback** (2026-11-05): the first run's `ubuntu-latest` job got
  403 from download.blender.org's CDN on all three attempts while the Windows and macOS
  jobs were served at once, and the same request is served from elsewhere, so the refusal looks tied to the runner's address.
  A mirror adds no trust to give, since its file must match the same pin, and the job
  never pretends to be anything but what it is to get past a refusal.
- **blender.org's 5.2 builds bundle Python 3.13**, on all three platforms; only a
  distribution's package may run on a system 3.14. The venv in CI is made from that 3.13,
  which Whittle accepts alongside 3.14 (Environment, above).
- **Only Linux x64 gates.** Windows and macOS have never been used for real, and Windows'
  Blender suite cannot finish on the headless runner, so they report without blocking. `publish` needs `tag` and `linux` only, which keeps them out of a release by
  construction rather than through how a failed `continue-on-error` job reports.
- **No Linux arm64 row**: Blender 5.2 publishes no such build. The lock has its wheels.
- **macOS has no GNU `timeout`**: `.github/scripts/shims/timeout` goes on `PATH` when the
  runner lacks a working one, so `run_tests.sh` and `build.sh` stay as they are and
  time-bounded. The only change they needed was `run_tests.sh` finding Windows' venv Python.
- **Windows checks out with `core.autocrlf` off**: CRLF would break the shell scripts.
- **The Blender archive's cache is restored and saved in separate steps**, since
  `actions/cache` saves only when a job passes and a failing platform would otherwise
  download Blender on every run.
- **CI publishes the documentation site** (2026-11-05), from `docs.yml`, to GitHub Pages at
  <https://imonalampshade.github.io/whittle/>. Why CI and not a hand: what goes public is then
  always a strict build of a commit on `main`, from the hash-pinned lock, with no `gh-pages`
  branch of generated files to review, and nothing is ever pushed from a machine. As with a
  release, the job holding the write permissions (`pages: write`, `id-token: write`) checks
  nothing out and has them alone.
- **The site tracks `main`, not the latest release** (2026-11-05), so it can describe things
  newer than what a user has installed. Why: there is one version of it to keep right, and a
  fix to a page reaches readers at once. The home page and the README say so.
- **A docs failure gates nothing** (2026-11-05): `docs.yml` stands alone, and `ci.yml` and
  `release.yml` do not know it. A failure leaves the site behind until the next good build,
  which can be many commits: nothing else builds the site, so a warning that reaches `main`
  fails every run until it is fixed, and a failed run is not retried. A stale site still beats
  a warning holding back a release. A run under way is never cancelled, so a deploy finishes;
  a run still waiting gives way to a newer one. One run per ref at a time keeps an older push
  from landing last, though re-running an old run rebuilds its own commit and puts that site
  back.
- **The docs job sets up an exact Python** (2026-11-05), 3.14.8, the one the site was first
  built on. The lock's Sphinx needs 3.13 or later, and `ubuntu-latest`'s own Python need not be.
- **No `.nojekyll`** (2026-11-05): a Pages site deployed by Actions serves the uploaded
  artifact as it is and runs no Jekyll, so `_static`, `_images`, `_modules` and `_sources`
  arrive whole. `upload-pages-artifact` drops dotfiles, which here is only Sphinx's `.buildinfo`.
- **Pull requests do not build the site** (2026-11-05): a broken page shows up when it reaches
  `main`, or on a `ci/**` push before that, and leaves the site behind until the next good
  build.
